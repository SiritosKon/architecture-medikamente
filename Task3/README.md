# Задание 3. Оценка Data Encryption at Rest and In Transit

Стратегия защиты данных для всей целевой системы (Task2). Классы C0–C4 и теги описаны в [Task1/data-protection.md](../Task1/data-protection.md).

## 1. Параметры классификации

Каждый набор данных оценивается по пяти осям.

1. **Чувствительность.** Классы:
   - C0 Public;
   - C1 Internal;
   - C2 Confidential;
   - C3 PII;
   - C4 Restricted — спецкатегория ПДн, врачебная тайна, идентификационные документы, секреты.
2. **Состояние:**
   - **at rest** — СУБД, объектное хранилище, бэкапы, логи, АРМ;
   - **in transit** — канал «клиент ↔ периметр», «сервис ↔ сервис», «контур ↔ партнёр», «филиал ↔ ЦОД»;
   - **in use** — данные в памяти приложения, на экране пользователя, в аналитическом ноутбуке.
3. **Профиль риска** = вероятность × ущерб.
   - Вероятность оценивается по доступности данных нарушителю: число пользователей, наличие внешнего канала.
   - Ущерб оценивается по правовым последствиям (КоАП 13.11, оборотные штрафы за утечки, 323-ФЗ, УК 137), репутации и стоимости восстановления.
   - Шкала: **Низкий / Средний / Высокий / Критический**.
4. **Правовой режим:**
   - 152-ФЗ (общие ПДн / спецкатегория);
   - 323-ФЗ (врачебная тайна);
   - 402-ФЗ, 54-ФЗ (бухучёт, ККТ);
   - PCI DSS (карты);
   - требования к СКЗИ (Приказ ФСБ № 378) и мерам (Приказ ФСТЭК № 21, УЗ-2).
5. **Объём и частота доступа:** массовые (журнал, аудит) или точечные (паспорт).

## 3. Матрица шифрования по хранилищам и каналам

### 3.1 At rest

| Хранилище | Уровень тома / диска | Уровень СУБД / объекта | Уровень поля | Ключи |
|---|---|---|---|---|
| Postgres (MPI, EHR, Scheduling, Payments, Consent) | LUKS (dm-crypt) на узлах; шифрованные диски облака | TDE (Postgres Pro Enterprise) или без TDE при LUKS + field-level | Vault Transit (AES-256-GCM) для C3/C4-колонок; per-patient DEK для EHR | KEK в Vault, мастер-ключ в HSM |
| MinIO / S3 (документы, Data Lake) | LUKS | SSE-KMS (KMS = Vault), Object Lock | Envelope encryption: DEK на пациента → crypto-shredding | Vault KMS |
| ClickHouse (аудит, витрины) | LUKS | Шифрованные диски ClickHouse (`encrypted` disk) | — (данные уже обезличены или содержат только идентификаторы) | Vault |
| Kafka | LUKS | — | Шифрование payload C4-полей продюсером (Vault Transit) | Vault |
| Elastic (логи) | LUKS | — | ПДн не пишутся (маскирование) | — |
| 1С (БП, ЗУП, УТ) | LUKS / BitLocker на сервере СУБД | СУБД Postgres в защищённом сегменте | — | Vault / HSM |
| АРМ сотрудников | BitLocker / Secret Net Studio (шифрование дисков), запрет локального хранения | — | — | TPM + AD |
| Мобильное приложение | Keychain / Android Keystore; кэш зашифрован; ПДн не кэшируются офлайн дольше сессии | — | — | Аппаратный keystore |
| Бэкапы | Иммутабельное хранилище | Шифрование клиентом (pgBackRest, restic) | — | Отдельный ключ в Vault |

### 3.2 In transit

| Канал | Протокол и защита |
|---|---|
| Пациент (браузер / приложение) ↔ WAF / API Gateway | TLS 1.3 (только AEAD), HSTS, OCSP stapling; в приложении — certificate pinning. Для работы с сертифицированными СКЗИ на периметре дополнительно ГОСТ TLS (КриптоПро NGate) для клиентов, которые его поддерживают |
| Сотрудники, филиалы ↔ контур | ГОСТ VPN (ViPNet Coordinator / Континент), поверх — TLS 1.3 к порталам; MFA |
| Сервис ↔ сервис (K8s) | mTLS (Istio, cert-manager, сертификаты на 24 ч), NetworkPolicy deny-by-default |
| Сервис ↔ Kafka / Postgres / ClickHouse / Vault | TLS 1.3 + аутентификация клиента по сертификату / SASL; динамические креды из Vault |
| Контур ↔ лаборатория | mTLS + OAuth2 client credentials + JWS-подпись тела; IP allowlist |
| Контур ↔ ПСП / ОФД / SMS-провайдер / ЕСИА | TLS 1.2+/1.3, подпись webhook (HMAC-SHA256), IP allowlist, договор поручения |
| 1С ↔ банк / ФНС / СФР | DirectBank / 1С-Отчётность: TLS + КЭП (ГОСТ Р 34.10-2012) на аппаратных токенах |
| ККТ ↔ сервер | Изолированный VLAN, ОФД по TLS; драйвер ККТ только на АРМ кассы |

### 3.3 In use

Данные в использовании — отдельная зона риска, которую шифрованием не закрыть.

| Мера | Что защищает |
|---|---|
| ABAC (OPA) и динамическое маскирование (PostgreSQL Anonymizer, API Gateway по тегам) | Пользователь получает на экран только то, что нужно для его задачи |
| DLP-агент | Экран, печать (watermark), буфер обмена, USB, почта |
| Запрет выгрузки из JupyterHub, аналитика только на L1/L2 | Аналитик не выносит данные наружу и не видит прямые ПДн |
| Маскирование в логах и дампах памяти (heap dump отключены в проде) | ПДн не оседают в журналах и диагностических файлах |
| Перспективно: confidential computing (Intel TDX / AMD SEV) для узлов с EHR | Данные в памяти недоступны даже администратору гипервизора |

## 4. Управление ключами

```
HSM / СКЗИ (мастер-ключ, root CA)
   └── Vault (auto-unseal через HSM)
         ├── KEK домена: ehr, identity, lab, payments, analytics, backup   ← ротация 1 раз в год, по инциденту — немедленно
         │      └── DEK: на пациента (EHR, документы) / на таблицу      ← ротация через rewrap без перешифровки данных
         ├── Transform (токенизация паспорт/СНИЛС/телефон, FPE)
         ├── PKI: сертификаты mTLS (TTL 24 ч), TLS периметра
         └── Database secrets: динамические логины Postgres/ClickHouse (TTL 1 ч)
```

- Разделение обязанностей. Администратор инфраструктуры не имеет доступа к ключам. Операции с мастер-ключом выполняются по схеме Shamir (3 из 5 ключедержателей).
- Crypto-shredding. При удалении по запросу субъекта или по истечении срока (Retention Service) уничтожается DEK пациента. Данные в СУБД, S3 и бэкапах становятся нечитаемыми.
- Все операции Vault пишутся в audit device → Audit Log → SIEM.

## 5. Автоматизированный контроль

| Что контролируем | Средство | Как | Реакция |
|---|---|---|---|
| Каждое поле классифицировано и защищено | **Privacy Gate** в CI/CD: OPA Conftest, Spectral (OpenAPI `x-data-classification`), проверка миграций Liquibase | Релиз падает при поле без тега, C4 в партнёрском контракте, C3/C4 без `protection` | Блок релиза; метрика `privacy_gate_violations_total` → VictoriaMetrics → Alertmanager |
| Нет незашифрованных хранилищ и открытых каналов | Policy-as-code для инфраструктуры: Kyverno / Gatekeeper в K8s, Checkov / tfsec для Terraform | Запрет PVC без шифрованного StorageClass, Service без mTLS, S3 без SSE, TLS < 1.2 | Admission deny; отчёт в SIEM |
| Нет секретов и ПДн в коде и логах | Gitleaks, Semgrep (правила на логирование `@Sensitive`), сканер логов в Elastic (regex + NER) | При каждом MR и непрерывно по логам | Блок MR; алерт при ПДн в логах |
| Где лежат ПДн (обнаружение «теневых» копий) | OpenMetadata PII auto-classification, DLP-сканирование общих ресурсов и АРМ (discovery) | Регулярное сканирование БД, бакетов, файловых шарингов | Задача владельцу домена; DLP-инцидент |
| Кто и как обращается к данным | Audit Log → SIEM + UEBA (Wazuh / MaxPatrol SIEM + правила на ClickHouse) | Базовые профили по роли; правила: массовый просмотр карт, доступ вне смены, break-glass, выгрузка > N записей, доступ к «VIP»-пациентам | Алерт DPO / ИБ; автоблок учётки при критичном срабатывании |
| Сертификаты и ключи | cert-manager, Vault (TTL), экспортер сроков сертификатов | Автоматическая ротация, алерт за 14 дней до истечения | Alertmanager |
| Уязвимости | Trivy / Grype (образы), сканер уязвимостей (MaxPatrol VM / RedCheck), DAST (OWASP ZAP) для API, включая BOLA-тесты | В CI и по расписанию | Блок образа с critical CVE; задача в трекер |
| Резервное копирование | Мониторинг pgBackRest, регулярный автоматический restore-тест | Ежедневно / еженедельно | Алерт при сбое |
| Сроки хранения | Retention Service по тегу `retention` | Ежедневные задания | Отчёт об удалённом; алерт при просрочке |
| Запросы субъектов | Privacy Request Handler | SLA-таймер 10 рабочих дней | Эскалация DPO |

## 6. Реестр программных и аппаратных средств защиты данных

Для ИСПДн УЗ-2 применяемые средства защиты информации должны пройти оценку соответствия (сертификация ФСТЭК), а криптографические средства — быть сертифицированными СКЗИ (ФСБ) там, где это требуется моделью угроз. Open-source компоненты применяются как прикладной слой. Их использование отражается в модели угроз и дополняется сертифицированными наложенными средствами.

| № | Средство | Тип | Назначение | Где применяется | Соответствие / примечание | Этап |
|---|---|---|---|---|---|---|
| 1 | **HSM** (напр. модули на базе ViPNet HSM / КриптоПро HSM) | Аппаратное | Хранение мастер-ключей, корневой CA, auto-unseal Vault | Ядро KMS | Сертифицированное СКЗИ | MVP |
| 2 | **HashiCorp Vault / OpenBao** | ПО | KMS, Transit / Transform (шифрование и токенизация), PKI, динамические секреты | Все сервисы | Open source; ключи защищены HSM | MVP |
| 3 | **КриптоПро CSP / NGate** | ПО / программно-аппаратное | ГОСТ TLS на периметре, КЭП | Периметр, АРМ бухгалтерии | Сертифицированное СКЗИ | 3–6 мес |

## 7. Итог

1. **Самый ценный класс — C4** (медицинские сведения, результаты анализов, косвенные медсведения, документы, ключи). Для него обязательны три уровня защиты: шифрование тома, шифрование поля с ключом на пациента и ABAC с аудитом на каждое обращение.
2. **In transit** всё шифруется всегда, в том числе внутри кластера (mTLS). На каналах с сотрудниками и филиалами используется ГОСТ-криптография.
3. **In use** закрывается минимизацией и маскированием, а не шифрованием. Пользователь получает только то, что ему нужно.
4. **Контроль автоматический.** Релиз не пройдёт без тегов, инфраструктура не примет незашифрованный том, нетипичный доступ порождает алерт. Удаление по запросу гарантирует crypto-shredding.
