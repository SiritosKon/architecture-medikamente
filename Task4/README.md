## 1. Анализ ситуации

### 1.1 Что мигрируем

| Сейчас | Целевое состояние (Task2) |
|---|---|
| Excel / сканы на общем диске: журнал, реестр, медкарты, анализы, платежи | Доменные сервисы на Java / Spring Boot в Kubernetes: MPI, Scheduling, EHR, Lab, Billing, CRM, Notification + Postgres, MinIO |
| 1С:БП и 1С:ТиС в файловом режиме, обмен файлами | 1С в клиент-серверном режиме на Postgres, интеграция через адаптер (HTTP-сервисы) |
| ККМ ↔ 1С через OLE-компоненту | Касса в VLAN + Billing, фискализация, ПСП для онлайн-оплаты |
| Один физический сервер в офисе: AD, файлы, Exchange, 1С | Облако / ЦОД в РФ (УЗ-2), филиалы через ГОСТ VPN |
| Защиты нет | Слой PbD: IAM, OPA, Vault, аудит, шифрование, Privacy Pipeline |
| Ручная аналитика в Jupyter | CDC → Privacy Pipeline → Lake / ClickHouse → BI / ML |

Цель — выдержать **пятикратный рост** объёма данных и числа пользователей: филиалы, десятки новых сотрудников, мобильное приложение.

### 1.2 Ключевые процессы и компоненты, затронутые миграцией

| Процесс | Компоненты | Критичность для производительности |
|---|---|---|
| Запись на приём (MVP) | Портал, API Gateway, Keycloak, OPA, Scheduling, MPI, Postgres | **Высокая**: публичный трафик, пики, SLA для пациента |
| Напоминания и подтверждения | Scheduling → Kafka → Notification → SMS / push / voice | **Высокая**: пакетные пики, внешние rate limits |
| Работа ресепшена | Портал ресепшена, маскирование, детокенизация | Средняя: массовые списки |
| Приём у врача (EHR) | АРМ врача, OPA (ABAC «лечащий врач»), EHR DB, S3 | Высокая: интерактивная работа, чтение больших карт |
| Оплата и фискализация | Billing, ПСП, ККТ, 1С-адаптер | **Высокая**: синхронный путь, внешние системы, 54-ФЗ |
| Интеграция с лабораторией | Partner API Gateway, Lab Integration | Средняя: асинхронно |
| Миграция данных | Excel / сканы → MPI / EHR, дедупликация | **Высокая** на этапе переноса |
| Аудит и SIEM | Kafka `audit.*` → ClickHouse → SIEM | Средняя: write amplification |
| Аналитика | CDC, Privacy Pipeline, ClickHouse | Средняя: не должна влиять на OLTP |

## 2. Выявленные проблемы по категориям

Коды совпадают с диаграммой. Для каждой причины указано, **как она проявится в производительности**.

### 1. Инфраструктура

| Код | Причина | Как проявится |
|---|---|---|
| I1 | Один физический сервер в офисе. В переходный период старая система (файлы, 1С, Exchange) и новая должны работать параллельно | Конкуренция за CPU, диск и сеть; один отказ останавливает обе системы |
| I2 | Канал офис / филиалы ↔ облако. ГОСТ VPN снижает пропускную способность, растёт RTT | Медленная загрузка порталов, таймауты у ККТ и 1С-клиентов в филиалах |
| I3 | Нет нагрузочного и DR-стенда | Узкие места впервые проявятся в продакшене |
| I4 | IOPS СУБД на шифрованных томах (LUKS + field-level) | Рост latency записи и чтения при пиках |
| I5 | Kubernetes без requests / limits, HPA, приоритетов | «Шумные соседи»: Privacy Pipeline или аналитика вытесняют Scheduling |

### 2. Данные и БД

| Код | Причина | Как проявится |
|---|---|---|
| D1 | Грязные Excel / сканы: дубли, разные написания ФИО, пустые поля | Долгий и ошибочный матчинг MPI при миграции; дубли пациентов ухудшают поиск |
| D2 | Общие ресурсы монолита, файловая 1С (`.1CD`) | Блокировки при одновременной работе; источник не выдерживает частых выгрузок |
| D3 | Поиск по зашифрованным полям (телефон, ФИО) без blind index | Full scan + расшифровка на каждый поиск ресепшена → секунды на запрос |
| D4 | Рост ×5 без партиционирования: записи, аудит, уведомления | Деградация запросов и vacuum, рост индексов |
| D5 | Dual write (Excel / 1С + новая система) в переходный период | Рассинхронизация, ручные сверки, повторные загрузки |

### 3. Архитектура и ПО

| Код | Причина | Как проявится |
|---|---|---|
| A1 | «Болтливые» синхронные вызовы: Scheduling → MPI → Consent → OPA → Vault по цепочке, N+1 при построении расписания | Latency складывается, хвосты p99 растут нелинейно |
| A2 | Запись + оплата как распределённая транзакция без саги | Блокировки, таймауты, «зависшие» слоты |
| A3 | Неверные границы доменов (общая БД на несколько сервисов) | Распределённый монолит: худшее из двух миров |
| A4 | Нет кэша расписания, справочников, публичных ключей JWKS | Лишняя нагрузка на БД и Keycloak |
| A5 | Не настроены пулы соединений (HikariCP ↔ Postgres max_connections), JVM, холодный старт | Исчерпание соединений при масштабировании pod-ов, всплески latency при деплое |

### 4. Интеграции

| Код | Причина | Как проявится |
|---|---|---|
| G1 | ККТ через OLE-компоненту 1С: синхронно, однопоточно, привязано к АРМ | Очередь на кассе, блокировка оплаты при сбое 1С |
| G2 | Обмен с файловой 1С на время миграции | Длинные выгрузки, блокировки ИБ |
| G3 | Rate limits внешних API: SMS / voice-провайдер, лаборатория, ПСП, ЕСИА | Отказы 429, недоставленные напоминания, задержки входа |
| G4 | Напоминания «за день» отправляются одним батчем в фиксированное время | Пик нагрузки на Notification, Kafka, провайдера |
| G5 | Нет идемпотентности и экспоненциального backoff | Шторм ретраев усиливает отказ; дубли SMS и платежей |

### 5. Безопасность (overhead мер PbD)

| Код | Причина | Как проявится |
|---|---|---|
| S1 | Синхронные OPA-решения и Vault-операции (decrypt / tokenize) на каждый запрос | +5…30 мс на вызов; при цепочке — сотни мс |
| S2 | Аудит каждого чтения C3 / C4 | Write amplification: каждое чтение порождает запись в Kafka и ClickHouse |
| S3 | Массовая детокенизация и расшифровка в списках ресепшена (расписание на день) | Сотни вызовов Vault на один экран |
| S4 | TLS / mTLS / ГОСТ TLS handshake без keep-alive и session resumption | CPU на периметре и sidecar-ах, рост latency |
| S5 | Тяжёлый Privacy Pipeline (k-анонимность, NER) | Конкуренция за ресурсы с OLTP (см. I5) |

### 6. Персонал

| Код | Причина | Как проявится |
|---|---|---|
| H1 | IT-отдел — 3 человека, архитектор = CTO (bus factor 1) | Медленная диагностика инцидентов производительности |
| H2 | Нет опыта эксплуатации K8s и Kafka под нагрузкой, нет SRE-практик | Ошибки конфигурации, долгий MTTR |
| H3 | Нет DBA и специалиста ИБ | Неоптимальные схемы, индексы, настройки Postgres |
| H4 | Сотрудники параллельно продолжают работать в Excel | Dual write (D5), недоверие к системе |
| H5 | Массовый найм: пользователи без обучения | Неэффективные сценарии, лишние запросы, ошибки |

### 7. Процессы

| Код | Причина | Как проявится |
|---|---|---|
| R1 | Нет нагрузочного тестирования, SLO и бюджета ошибок | Нет критерия «готово к запуску» |
| R2 | Риск миграции «big bang» вместо поэтапной (Strangler Fig) | Вся нагрузка сразу на незрелую систему, откат невозможен |
| R3 | Нет базовых метрик текущей системы | Нельзя доказать улучшение или ухудшение |
| R4 | Нет capacity planning под график открытия филиалов | Ресурсы заканчиваются внезапно |
| R5 | Ручные релизы без canary и feature flags | Регрессии производительности сразу у всех пользователей |

### 8. Нагрузка и бизнес-факторы

| Код | Причина | Как проявится |
|---|---|---|
| B1 | Пики записи: утро понедельника, момент открытия расписания | Burst на Scheduling, гонки за слоты |
| B2 | Всплески от push-рассылок мобильного приложения | Одновременный вход тысяч пользователей → Keycloak, API |
| B3 | Открытие филиалов волнами | Скачкообразный рост пользователей и данных |
| B4 | Сезонность (ОРВИ, диспансеризация) | Кратный рост записей в отдельные месяцы |
| B5 | Аналитика и ML на тех же ресурсах, что и OLTP | Тяжёлые запросы мешают онлайн-процессам |

## 3. Рекомендации и приоритизация

Приоритет определён по матрице **влияние на производительность и доступность × вероятность** с учётом трудоёмкости.

- **P1** — сделать до запуска MVP: высокое влияние и высокая вероятность, либо блокирует запуск.
- **P2** — до открытия второго филиала / мобильного приложения.
- **P3** — к финальному состоянию (≈ 1 год).

| № | Мера | Устраняет | Влияние | Трудоёмкость | Приоритет |
|---|---|---|---|---|---|
| 1 | **Strangler Fig** вместо «big bang»: сначала только запись (MVP) через новую систему, Excel-журнал в read-only; далее по доменам (EHR → лаборатория → оплата). Anti-corruption layer к 1С | R2, D5, H4 | Высокое | Среднее | **P1** |
| 2 | **Нагрузочное тестирование** (k6 / Gatling) по профилю ×5 и ×10 для пиков B1 / B4. **SLO**: запись p95 < 500 мс, доступность 99,9 %; бюджет ошибок. Базовые метрики текущей системы снять до миграции | R1, R3, I3, B1 | Высокое | Среднее | **P1** |
| 3 | Вынести систему из офиса в **облако / ЦОД в РФ** (аттестованное под УЗ-2) с отдельным нагрузочным стендом; офисный сервер оставить только для AD / печати на переходный период | I1, I3 | Высокое | Среднее | **P1** |
| 4 | **Асинхронность и события**: напоминания и подтверждения — через Kafka; **сага** для «запись → оплата» (оркестрация, компенсации); outbox-паттерн вместо dual write | A2, G4, D5 | Высокое | Среднее | **P1** |
| 5 | **Размазать напоминания по времени** (jitter, окна отправки, приоритеты), очереди с rate limiter под лимиты провайдера; резервный SMS-провайдер | G4, G3 | Высокое | Низкое | **P1** |
| 6 | **Оптимизация privacy-overhead**: OPA как sidecar с локальным бандлом политик (решение < 1 мс), кэш решений; Vault Transit batch API; blind index (HMAC) для поиска по телефону / ФИО; маскирование без детокенизации там, где полное значение не нужно | S1, S3, D3 | Высокое | Среднее | **P1** |
| 7 | **Асинхронный аудит**: события в Kafka (fire-and-forget с гарантией доставки через outbox), батч-вставка в ClickHouse, партиционирование по дате; аудит на уровне запроса-списка, а не каждой строки | S2, D4 | Среднее | Низкое | **P1** |
| 8 | **Качество данных до миграции**: профилирование Excel, правила очистки, вероятностный матчинг MPI (ФИО + ДР + телефон), ручная очередь спорных дублей, пробные прогоны | D1 | Высокое | Среднее | **P1** |
| 9 | **Команда**: нанять SRE / DevOps, DBA (Postgres), специалиста ИБ; на период миграции привлечь внешнего архитектора / интегратора; runbooks и дежурства | H1, H2, H3 | Высокое | Высокое (бюджет выделяется) | **P1** |
| 10 | **Касса**: вынести фискализацию из OLE-интеграции — ККТ через драйвер / облачную кассу по сетевому API, асинхронная передача в 1С через адаптер; очередь при недоступности 1С | G1, G2 | Высокое | Среднее | **P1** |
| 11 | Перевод **1С в клиент-серверный режим** на Postgres; обмен через HTTP-сервисы / OData вместо файлов | D2, G2 | Среднее | Среднее | P2 |
| 12 | **Kubernetes-гигиена**: requests / limits, HPA по RPS и latency, PodDisruptionBudget, PriorityClass (OLTP > аналитика), отдельные node pool для аналитики и Privacy Pipeline | I5, S5, B5 | Среднее | Низкое | P2 |
| 13 | **Кэширование**: расписание и свободные слоты (Redis с коротким TTL + инвалидация по событиям), справочники, JWKS; CDN для статики портала | A4, B1, B2 | Среднее | Низкое | P2 |
| 14 | **Пулы и JVM**: PgBouncer, согласование HikariCP × число pod-ов, readiness / startup probes, прогрев, CDS / CRaC или GraalVM native для быстрых стартов | A5 | Среднее | Низкое | P2 |
| 15 | **Сеть**: достаточная полоса и резервный канал для филиалов, аппаратный ГОСТ VPN, keep-alive, HTTP/2, TLS session resumption, терминация TLS на периметре | I2, S4 | Среднее | Среднее | P2 |
| 16 | **Устойчивость интеграций**: идемпотентные ключи, retry с экспоненциальным backoff + jitter, circuit breaker (Resilience4j), bulkhead, таймауты; контрактные тесты с партнёрами | G5, G3 | Среднее | Низкое | P2 |
| 17 | **Правильные границы доменов** (DDD): database-per-service, запрет общих таблиц; API-композиция через BFF вместо цепочек; агрегированные эндпоинты против N+1 | A1, A3 | Высокое | Высокое | P2 |
| 18 | **CI/CD**: canary / blue-green, feature flags, автоматический откат по SLO; performance-тесты в пайплайне | R5 | Среднее | Среднее | P2 |
| 19 | **Capacity planning**: модель нагрузки на филиал (пациенты / день, пользователи), квартальный пересмотр, автоскейлинг облака | R4, B3 | Среднее | Низкое | P2 |
| 20 | **Хранилища**: партиционирование (записи, уведомления, аудит — по месяцу), архивирование, реплики чтения Postgres для отчётов, NVMe-диски с запасом IOPS | D4, I4 | Среднее | Среднее | P2 |
| 21 | **Изоляция аналитики**: только CDC → Lake / ClickHouse, никаких запросов в OLTP; Privacy Pipeline по расписанию вне пиков | B5, S5 | Среднее | Низкое | P3 |
| 22 | **Обучение и change management**: обучение ресепшена и врачей, «чемпионы» в филиалах, отключение Excel после стабилизации | H4, H5 | Среднее | Низкое | P3 |
| 23 | **Защита от всплесков мобильного трафика**: rate limit на API Gateway, очереди, graceful degradation (read-only расписание), push-рассылки порциями | B2 | Среднее | Низкое | P3 |

## 4. План по этапам

```
Месяц 0–2 (MVP)          │ P1: Strangler Fig (только запись), облако РФ, нагрузочные тесты + SLO + baseline,
                         │     Kafka + outbox + сага, jitter напоминаний, OPA sidecar, blind index, async audit,
                         │     очистка данных и MPI, найм SRE/DBA/ИБ, план по ККТ
Месяц 2–6 (филиал №2)    │ P2: 1С клиент-сервер, K8s-гигиена, кэш, пулы, сеть филиалов, resilience-паттерны,
                         │     DDD-границы для EHR/Billing, canary, capacity planning, партиционирование
Месяц 6–12 (финал)       │ P3: изоляция аналитики, обучение и отключение Excel, мобильное приложение
                         │     с защитой от всплесков; регулярный пересмотр SLO
```

## 5. Метрики контроля

| Метрика | Цель | Источник |
|---|---|---|
| Latency создания записи (p95 / p99) | < 500 мс / < 1 с | API Gateway, VictoriaMetrics |
| Доступность портала и API | ≥ 99,9 % | Blackbox-мониторинг |
| Время OPA-решения (p99) | < 5 мс | OPA metrics |
| Время Vault-операции (p99) | < 20 мс | Vault telemetry |
| Лаг Kafka-консьюмеров (Notification, Audit) | < 1 мин | Kafka exporter |
| Доля доставленных напоминаний за T−24 ч | ≥ 99 % | Notification |
| Время фискализации чека | < 3 с | Billing |
| Насыщение пулов соединений БД | < 80 % | Postgres / PgBouncer exporter |
| Дубли пациентов после миграции | < 0,5 % | MPI |
| Ошибки 5xx / 429 внешних интеграций | < 0,1 % / без роста | API Gateway |

## 6. Вывод

Главные риски производительности связаны не с технологиями микросервисов, а с тремя вещами:

1. **Способ миграции.** Переход «big bang» и dual write создают риск, который закрывает Strangler Fig и outbox.
2. **Незрелость эксплуатации.** Нет нагрузочных тестов, SLO и SRE. Это закрывают тестирование, SLO, найм и canary.
3. **Накладные расходы новых мер защиты**: синхронные OPA / Vault, аудит, поиск по зашифрованным данным. Они снимаются локальными политиками, batch-операциями, blind index и асинхронным аудитом.

Меры P1 обязательны до запуска MVP. Без них система не выдержит даже первого пика записи, не то что пятикратного роста.
