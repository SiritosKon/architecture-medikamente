# Данные для защиты, способы защиты и механизм тегирования

## 1. Конфиденциальные данные, не учтённые во внутренних системах

Сейчас ни одна система не знает, *какие* данные она хранит. Классификации нет, владельцев нет, сроков хранения нет. Ниже приведены данные, найденные при анализе процессов (DFD-00…08).

| # | Категория | Состав | Где лежит сейчас | Правовой статус | Учтено в системах? |
|---|---|---|---|---|---|
| 1 | Контактные ПДн пациента | ФИО, дата рождения, пол, телефон, email | D1 журнал, D2 реестр (xlsx), D3 почта, D7 платежи | ПДн (152-ФЗ) | ❌ нет владельца, есть дубли |
| 2 | Расширенный профиль | Адрес регистрации, место работы / учёбы | D2 реестр, D5 сканы анкет | ПДн | ❌ |
| 3 | Идентификационные документы | Паспорт (серия, номер, кем выдан), СНИЛС, полис ОМС/ДМС, ИНН | D5 сканы, D2 реестр | ПДн, повышенный риск (кража личности) | ❌ хранятся полные сканы |
| 4 | Медицинские сведения | Жалобы, анамнез, **хронические заболевания**, диагнозы (МКБ-10), назначения, заключения | D4 медкарты, D2 реестр (!), D3 почта, D10 копии | **Спецкатегория** (152-ФЗ ст. 10) + **врачебная тайна** (323-ФЗ ст. 13) | ❌ смешаны с общими ПДн |
| 5 | Результаты анализов | Лабораторные показатели, PDF-бланки | D6, D4, общий ящик D3 | Спецкатегория + врачебная тайна | ❌ по две копии и больше |
| 6 | Косвенные медицинские сведения | Запись к конкретному специалисту (онколог, венеролог, психиатр), перечень услуг в счёте, списание препарата или импланта на пациента | D1, D7, D9 | Позволяют *вывести* диагноз → защищать как спецкатегорию | ❌ не распознаются как медданные |
| 7 | Договоры и согласия | Договор на оказание услуг, согласие на обработку ПДн, ИДС на вмешательство | D5 сканы, бумажный архив | ПДн + юридически значимые документы | ❌ нет структурированных цели и срока согласия |
| 8 | Платёжные данные | Сумма, способ оплаты, дата, связь с пациентом, данные для налогового вычета | D7 xlsx, D8 1С | ПДн + коммерческая тайна | ⚠ частично в 1С, дубль в Excel |
| 9 | Карточные данные | PAN, срок действия | Только в POS-терминале банка | PCI DSS | ✅ вне периметра, сохранить |
| 10 | Кадровые ПДн сотрудников | Паспорт, СНИЛС, ИНН, адрес, реквизиты, зарплата, **медицинские книжки**, больничные | D8 1С:БП, сканы личных дел | ПДн; сведения о здоровье — спецкатегория | ⚠ в 1С без разделения прав |
| 11 | Учётные данные и секреты | Пароли домена, КЭП бухгалтера, ключи клиент-банка, доступы к ОФД | АРМ, реестр Windows | Критичные для ИБ | ❌ |
| 12 | Аналитические выгрузки | Сводные таблицы с ФИО, ноутбуки Jupyter | D10 ноутбук аналитика, почта | ПДн (не обезличены) | ❌ неизвестное число копий |
| 13 | Журналы и логи | Логи 1С, Exchange, файлового сервера (если ведутся) | Сервер | Могут содержать ПДн | ❌ не централизованы |

## 2. Классификация (уровни конфиденциальности)

| Уровень | Название | Описание | Примеры |
|---|---|---|---|
| **C0** | Public | Можно публиковать | Прайс-лист, расписание работы филиалов, ФИО и специальность врачей на сайте |
| **C1** | Internal | Внутренние данные без ПДн | Остатки ТМЦ, справочники услуг, агрегированные метрики |
| **C2** | Confidential | Коммерческая тайна, финансы | Платежи без медицинских сведений, P&L, договоры с поставщиками |
| **C3** | Personal (PII) | ПДн общей категории | Контакты пациента, расширенный профиль, кадровые ПДн без сведений о здоровье |
| **C4** | Restricted (PHI / Special) | Спецкатегория ПДн, врачебная тайна, идентификационные документы, секреты | Диагнозы, анамнез, результаты анализов, косвенные медсведения, паспорт/СНИЛС, мед. книжки, ключи |

## 3. Список данных для защиты и способы защиты

Условные обозначения:

- **Шифрование** — обратимое преобразование, доступ по ключу: AES-256-GCM at rest, TLS 1.3 / ГОСТ TLS in transit.
- **Обфускация / маскирование** — данные хранятся целиком, но показываются частично в зависимости от роли (динамическое маскирование): `+7 *** ***-**-12`, `Иванов И.`.
- **Псевдонимизация** — прямой идентификатор заменяется токеном (`patient_token`, `order_id`). Обратное сопоставление возможно только через защищённый токен-стор.
- **Обезличивание (анонимизация)** — необратимое преобразование для аналитики: обобщение, агрегация, k-анонимность, удаление прямых идентификаторов, NER-редакция свободного текста.

| Данные | Класс | Шифрование | Обфускация / маскирование | Псевдонимизация / обезличивание | Комментарий |
|---|---|---|---|---|---|
| ФИО | C3 | at rest (TDE / LUKS) + TLS | Ресепшен, касса, уведомления: `Иванов И.` | В сервисах записи, оплаты, склада — `patient_token`; в аналитике удаляется | Полное ФИО видят лечащий врач и сам пациент |
| Дата рождения | C3 | at rest + TLS | `**.**.1985` | Для лаборатории и аналитики — возрастная группа (`age_band`) | Нужна для идентификации при визите |
| Телефон, email | C3 | **field-level** (Vault Transit) | `+7 *** ***-**-12`, `i***@mail.ru` | Детокенизация — только у сервиса уведомлений | Самый частый вектор утечки при выгрузках |
| Адрес, место работы/учёбы | C3 | field-level | Скрыт для всех, кроме оформления договора / ДМС | Аналитика: город / район | Собирать только при необходимости (Data Minimization) |
| Паспорт, СНИЛС, полис | C4 | field-level + отдельный ключ | Показываются последние 4 цифры | Хранится токен + флаг `verified`; сканы не хранятся | Сверка при визите вместо копирования |
| Диагноз (МКБ-10), анамнез, хронические заболевания, заключения | C4 | field-level (per-patient DEK, envelope encryption) + TLS | Не показываются вне EHR | Аналитика: только коды МКБ верхнего уровня в агрегатах, k ≥ 5 | Доступ по ABAC «лечащий врач» |
| Результаты анализов | C4 | field-level + подпись (JWS) при передаче | В уведомлениях — только «результат готов» | Для лаборатории — `order_id` вместо ФИО | Пациент видит только свои (patient_id = sub) |
| Запись к специалисту / перечень услуг | C4 (косвенно) | at rest + TLS | Ресепшен видит специализацию только своего филиала; в SMS специализации нет | В счёте и 1С — коды услуг без диагноза | Косвенный признак диагноза |
| Договор, согласия | C3 | S3 SSE-KMS, per-patient DEK | — | — | Crypto-shredding при удалении |
| Платежи | C2 | at rest + TLS | Кассир видит только текущий платёж | `patient_token` вместо ФИО | Excel-дубль упраздняется |
| Кадровые ПДн | C3 / C4 | СУБД 1С на шифрованном томе | Бухгалтерия видит суммы, не видит мед. книжки | — | Отдельная ИБ 1С:ЗУП |
| Секреты, ключи, КЭП | C4 | Vault / HSM, аппаратные токены | — | — | Ротация, запрет хранения в коде |
| Логи и трассировки | C3 | at rest | Автоматическое маскирование ПДн в логгере по тегам | — | ПДн в логи не пишутся |
| Аналитические данные | C1–C2 после обработки | at rest (S3 / ClickHouse) | — | **Обезличивание** в Privacy Pipeline | Ре-идентификация по заявке, одобряет DPO |

## 4. Механизм тегирования данных

### 4.1 Таксономия тегов

Каждое поле (колонка БД, поле API или события, атрибут в озере) получает набор тегов:

```yaml
# фрагмент словаря тегов (хранится в Data Catalog и в Git как code)
classification: [C0, C1, C2, C3, C4]     # уровень конфиденциальности
category:
  - pii.contact        # ФИО, телефон, email
  - pii.profile        # адрес, работа
  - pii.identity       # паспорт, СНИЛС, полис
  - pii.pseudo         # токен вместо идентификатора
  - phi.diagnosis      # диагноз, МКБ-10
  - phi.anamnesis      # анамнез, хронические заболевания
  - phi.lab            # результаты анализов
  - phi.indirect       # косвенные медсведения (специализация, услуга)
  - fin.payment
  - hr.pii | hr.health
  - legal.consent
legal_basis: [152fz.art6, 152fz.art10, 323fz.art13, 402fz, 54fz]
protection:  [encrypt_field, mask, tokenize, anonymize, none]
retention:   P25Y | P5Y | P75Y | P14D ...   # ISO-8601 срок хранения
consent:     [treatment, notifications, marketing]   # требуемое согласие
owner:       domain-scheduling | domain-ehr | ...
```

Сроки хранения (ориентиры для тега `retention`):

| Данные | Срок |
|---|---|
| Медицинская карта амбулаторного пациента | 25 лет |
| Первичные бухгалтерские документы | 5 лет (402-ФЗ) |
| Кадровые документы | 50/75 лет |
| Сырые данные в raw-зоне аналитики | 14 дней |

### 4.2 Где живут теги и как они применяются

| Слой | Инструмент | Как ставится тег | Что делает тег (enforcement) |
|---|---|---|---|
| Каталог (единый источник истины) | **OpenMetadata** (Classification & Tags, Glossary, Lineage) + автоклассификатор PII | Автосканирование колонок и ручное подтверждение владельцем домена | Хранит политику, строит Lineage, показывает, где находятся C4-данные |
| PostgreSQL (сервисы) | `SECURITY LABEL` + расширение **PostgreSQL Anonymizer**, `COMMENT ON COLUMN`, pgcrypto / Vault Transit | Миграции Liquibase/Flyway содержат метки | Динамическое маскирование для ролей, RLS по `branch_id`, pgaudit на C4-таблицах |
| API (OpenAPI 3) | Расширение `x-data-classification`, `x-data-category` на полях схем | В контракте API | API Gateway фильтрует и маскирует поля по scope клиента; Spectral-линтер запрещает поле без тега |
| Код (Java / Spring) | Аннотации `@Sensitive(category = PHI_DIAGNOSIS)` на DTO | Генерируются из OpenAPI | Jackson-сериализатор маскирует, логгер (Logback masking) вырезает, `toString()` безопасен |
| События (Kafka) | Метаданные полей в схеме Avro/Protobuf (Schema Registry, Apicurio) | В схеме события | Консьюмер без права на тег получает поле зашифрованным; Privacy Pipeline решает, как обезличить |
| Хранилище объектов (S3/MinIO) | Object tags `classification=C4` | При загрузке | Политика бакета, SSE-KMS, lifecycle по `retention` |
| Аналитика (ClickHouse, Iceberg) | Column comments + политики доступа, row policies | Наследуются из каталога через Lineage | Маскирование, запрет `SELECT` C3/C4-колонок ролям BI |
| Инфраструктура | Kubernetes labels `data-classification: c4` на namespace и pod | В Helm-чартах | NetworkPolicy, отдельные узлы, сбор аудита |

Пример метки колонки:

```sql
SECURITY LABEL FOR anon ON COLUMN patient.phone
  IS 'MASKED WITH FUNCTION anon.partial(phone, 2, $$******$$, 2)';
COMMENT ON COLUMN patient.phone IS
  'classification=C3; category=pii.contact; protection=encrypt_field,mask; retention=P25Y';
```

Пример фрагмента API-контракта:

```yaml
LabOrder:
  type: object
  properties:
    orderId:   { type: string, x-data-classification: C1, x-data-category: pii.pseudo }
    sex:       { type: string, x-data-classification: C3, x-data-category: pii.profile }
    ageBand:   { type: string, x-data-classification: C1 }
    testCodes: { type: array, items: {type: string}, x-data-classification: C1 }
  # поля fullName, birthDate, diagnosis в партнёрском контракте запрещены правилом линтера
```

### 4.3 Автоматическая проверка релиза (release privacy gate)

Проверка реализует требование финального состояния: «релиз проверяется в автоматическом режиме на работу с тегированными данными, после чего информация передаётся в систему мониторинга и алертинга». Шаги пайплайна CI/CD (GitLab CI / GitHub Actions):

1. **Schema diff**: новые колонки в миграциях и поля в OpenAPI/Avro без тега `classification` → сборка падает.
2. **Policy-as-code (OPA / Conftest)**:
   - поле C4 нельзя добавить в партнёрский контракт;
   - C3/C4 без `protection` запрещены;
   - сервису, не входящему в домен-владелец, нельзя читать C4.
3. **SAST и секреты**: Semgrep-правила на логирование `@Sensitive`-полей, Gitleaks.
4. **Интеграционный тест маскирования**: запрос под ролью `reception` не должен вернуть полный телефон или диагноз.
5. **Публикация результатов**: метрики `privacy_gate_violations_total{service,tag}` в **VictoriaMetrics**, изменения Lineage в OpenMetadata. При нарушении **Alertmanager** уведомляет DPO и команду.

## 5. Инструменты, способы и меры по потокам

Меры привязаны к шагам целевых DFD (`dfd/to-be/`).

| Поток / этап | Меры и инструменты |
|---|---|
| Пациент ↔ портал / мобильное приложение (DFD-01, 03, 04) | TLS 1.3 (HSTS, certificate pinning в приложении); Keycloak (OIDC + PKCE, OTP / ЕСИА, MFA); WAF; rate limit; защита от BOLA (id из токена); в push/SMS нет медсведений |
| Сотрудник ↔ АРМ / порталы (DFD-01, 03, 05, 06) | SSO Keycloak ↔ AD, MFA, персональные учётки (без общих); RBAC + ABAC (OPA); динамическое маскирование; DLP-агент (USB, печать с watermark, почта); ГОСТ VPN для филиалов |
| Сервис ↔ сервис (все) | mTLS (service mesh Istio/Linkerd), NetworkPolicy, сервисные учётки с минимальными правами, Kafka с TLS + ACL на топики по тегам |
| Хранение в СУБД (D1′…D9′) | LUKS/TDE, field-level шифрование C3/C4 (Vault Transit, envelope encryption), pgaudit, RLS, PostgreSQL Anonymizer, шифрованные бэкапы (pgBackRest + ключ из Vault), DR-копия в другой зоне РФ |
| Документы и сканы (D11′) | S3/MinIO SSE-KMS, per-patient DEK → crypto-shredding, object lock (WORM) для подписанных документов, антивирусная проверка при загрузке |
| Интеграция с лабораторией (DFD-04) | Договор поручения; Partner API Gateway (mTLS + OAuth2 client credentials, scopes), псевдонимизация (`order_id`), JWS-подпись, валидация схемы, idempotency-key, запрет ПДн в URL и логах |
| Уведомления (DFD-01) | Минимальный текст; проверка согласия в Consent Service; детокенизация контакта только ролью `notifier`; договор поручения с SMS/voice-провайдером |
| Оплата (DFD-05) | Redirect/iframe ПСП (PAN не входит в контур), подпись webhook (HMAC), ККТ в изолированном VLAN, 1С в клиент-серверном режиме в защищённом сегменте |
| Кадры (DFD-06) | Отдельная ИБ 1С:ЗУП, КЭП на аппаратных токенах, DirectBank вместо файлов, портал сотрудника |
| Согласия и права субъекта (DFD-02) | Consent Service, Privacy Request Handler (SLA 10 рабочих дней), Retention Service по тегу `retention`, событие `privacy.erase` / `stop-processing` в Kafka |
| Аналитика (DFD-08) | CDC (Debezium) → Privacy Pipeline (HMAC-псевдонимы, обобщение, k-анонимность, NER-редакция для LLM) → озеро (Iceberg) и витрины (ClickHouse). OpenMetadata Lineage; JupyterHub без выгрузки; on-prem LLM |
| Аудит и мониторинг (все) | Append-only журнал (ClickHouse, WORM) → SIEM (Wazuh / MaxPatrol SIEM) + UEBA, VictoriaMetrics + Alertmanager. Алерты: массовый просмотр карт, доступ вне смены, break-glass, выгрузки больше N записей, нарушения privacy gate |
